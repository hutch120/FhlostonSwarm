1. Executive Summary

The Client platform is an AI-driven workforce-capability platform. Administrators configure projects containing AI persona and scenario "work models", and learners complete AI-judged role-play exercises whose results are scored against an AI-generated benchmark. Because the platform's core value is an AI-generated capability score, this assessment treated the AI/LLM attack surface as a first-class risk area, assessed alongside traditional web application and API security.

AI/LLM testing outcome

The AI scoring model was tested directly in the live application. A combined attack that attempted to override the AI judge's instructions, force a perfect score, and extract the system prompt and grading rubric was submitted as a learner response. The attack failed: the AI judge scored the submission on its actual content, awarded no inflated score, and disclosed no internal instructions. This indicates that the scoring model is resistant to the direct prompt-injection technique tested.

Overall risk posture: Low to Moderate. No Critical or High severity vulnerabilities were found open. The highest-rated issues are Medium, and none exposes sensitive user data or allows privilege escalation. The remaining findings are Medium or lower and are primarily defense-in-depth and hardening items (security headers, session handling, error handling and information exposure).

Key business risks

  1. Project metadata exposure (F-01). Basic project details, including the workspace identifier, can be retrieved by unauthenticated users and by unrelated authenticated users.
  2. Internal engineering information in the production client (F-02). The publicly delivered web client contains developer documentation and diagnostic code that would reduce the effort required for a future attacker's reconnaissance.
  3. Session handling hardening (F-04, F-05). Sessions cannot be revoked server-side at logout, and the session token is readable by client-side scripts. Neither is exploitable on its own today, but both amplify the impact of any future script-injection flaw.

2. Positive Findings & Effective Controls

What the platform does well

  • AI judge resists prompt injection. A live "system override" attack combining score manipulation and system-prompt/rubric extraction was rejected. The submission was scored on its merits, and no internal instructions were revealed.
  • Strong transport security. All in-scope hosts accept only TLS 1.2 and TLS 1.3 with strong cipher suites and valid certificates.
  • Privilege escalation is blocked. A standard user attempting to assign themselves Owner, Admin or Editor roles was correctly rejected, as was access to the administrative area.
  • Sensitive diagnostics endpoint is well protected. The internal health/diagnostics endpoint rejected both anonymous callers and the administrator test account, indicating it is restricted to a higher privilege tier.
  • Private resources are access-controlled. Private-tagged project data and per-user result listings are correctly scoped to the requesting user, and private scenario results are only available to the users involved in them.
  • Sound backend input handling. Testing of input handling showed type-level rejection of malformed parameters, consistent with parameterised database queries. No injection or cross-site scripting vulnerabilities were identified.
  • Secure cookie baseline. The session cookie is issued with the Secure and SameSite=Strict attributes, and no credentials or API secrets were found hard-coded in the client application.
  • Web server posture. Probing for common sensitive files (environment files, source-control data, configuration and backup files) found none exposed, no separate administrative panel was reachable, the automated vulnerability scan raised no high-confidence issues, and all hosts are fronted by a content delivery network.

3. Scope & Methodology

The assessment followed a structured methodology covering six phases: reconnaissance, unauthenticated vulnerability assessment, authenticated testing, AI/LLM security testing, business logic and privilege escalation testing, and reporting. Testing was non-destructive and used only synthetic test data belonging to the provisioned test accounts. This dynamic testing was supplemented by static code analysis of the client's three application repositories (see Section 7).

5. AI/LLM Security Testing

Results are mapped to the OWASP Top 10 for LLM Applications. Large language model output is non-deterministic, so a single blocked attempt demonstrates resilience to that specific technique but does not guarantee that every variation would be blocked.

AI-01 — Direct prompt injection, score manipulation and system-prompt extraction

CONTROL EFFECTIVE

OWASP LLM mapping: LLM01 Prompt Injection; LLM06 Sensitive Information Disclosure
Component: AI scoring / judging model used for learner scenario results

Test performed

As a standard user, a learner response was submitted to a live scenario containing a combined attack payload. The payload impersonated a "system override", instructed the model to ignore its scenario, rubric and benchmark, demanded a fixed perfect score and approval message, and requested the model's system prompt and grading instructions verbatim.

Result

  • The platform scored the response on its actual content, rating it far below the benchmark on every capability dimension and showing a "benchmark not reached" outcome.
  • No perfect score was awarded and the demanded approval message did not appear anywhere in the user interface or API responses reviewed.
  • No system prompt, rubric text or other internal configuration was disclosed in the user interface or in the underlying API responses.

Conclusion

The scoring model evaluates the semantic content of a submission rather than following instructions embedded in it. This is a strong and positive result for the integrity of the platform's central feature: AI-generated capability scores.

6. Technical Findings

F-01 — Project metadata disclosed to unauthenticated and unrelated users

MEDIUM

Component: Project lookup API endpoint  |  Mapping: OWASP API1:2023 Broken Object Level Authorization (read-only)

Description

The endpoint that returns project details returns the same information whether the caller is unauthenticated, an unrelated standard user, or the project's own administrator. Returned fields include the project name, the internal project identifier, the workspace identifier, the access tier and module count. The project involved is tagged as "unlisted", and access checks that exist for "private" projects are not applied to this tier. By contrast, the endpoint that lists a user's own projects is correctly scoped to the caller, so this is an endpoint-specific gap rather than a systemic authorization weakness.

Impact

Project details and internal identifiers are exposed to anyone who obtains or guesses a project identifier. The exposed fields are low sensitivity, but they assist reconnaissance, and the missing authorization check means any future sensitive field added to this response would also be exposed.

Recommendation

Apply the same creator/role/administrator authorization already used for private projects to unlisted projects. If "unlisted" is intended to be shareable by link, treat the identifier as an unguessable secret and remove the remaining identifying fields, in particular the workspace identifier, from the response.

F-02 — Internal developer documentation and diagnostic code shipped in the production web client

MEDIUM

Component: Production JavaScript bundle  |  Mapping: OWASP A05:2021 Security Misconfiguration

Description

The JavaScript delivered to every visitor contains a detailed developer-authored access-control reference covering most backend API endpoints, including notes on known or suspected gaps and internal test identifiers. It also contains the source of an internal diagnostics and self-test harness that describes the backend's technology stack and dependencies. No hard-coded credentials were found in the bundle.

Impact

This material is not required by end users and gives an attacker a ready-made map of the API surface and the areas the engineering team considered weakest, reducing the effort needed for further attacks.

Recommendation

Exclude developer-only documentation and diagnostic modules from production builds, and keep such content in internal tooling that is never delivered to clients.

F-03 — Missing HTTP security headers on all hosts

MEDIUM

Component: All in-scope hosts  |  Mapping: OWASP A05:2021 Security Misconfiguration

Description

None of the tested hosts return Content-Security-Policy, X-Frame-Options, Strict-Transport-Security, X-Content-Type-Options, Referrer-Policy or Permissions-Policy. This was confirmed manually and by automated scanning.

Impact

The application is exposed to clickjacking and lacks a defense-in-depth layer against content-injection attacks and protocol downgrade.

Recommendation

Configure a response-headers policy at the content delivery layer that sets at minimum Strict-Transport-Security, X-Content-Type-Options: nosniff, a clickjacking control (X-Frame-Options: DENY or CSP frame-ancestors), and a baseline Content-Security-Policy.

F-04 — No server-side logout or session revocation

MEDIUM

Component: Authentication and session management

Description

There is no server-side logout operation. Signing out only removes the token from the browser, and the token remains valid against the API for its full lifetime (one hour).

Impact

A token captured from a shared device, logs or a future script-injection flaw cannot be invalidated by the legitimate user signing out.

Recommendation

Implement server-side token revocation on logout, for example a token deny-list, or short-lived access tokens paired with revocable refresh tokens.

F-05 — Session token stored in a script-readable cookie

MEDIUM

Component: Client-side session handling

Description

The session token is written to a cookie by client-side JavaScript, which means it cannot carry the HttpOnly attribute and can be read by any script running on the page. The cookie is also scoped to the parent domain rather than only the application's own host. No cross-site scripting vulnerability was found during testing, so this is a defense-in-depth weakness rather than an exploitable flaw.

Recommendation

Issue the session token from the server in a Set-Cookie header with HttpOnly, Secure and SameSite=Strict, scoped to the narrowest practical domain.

F-06 — User enumeration through the password-reset function

LOW-MEDIUM

Component: Password-reset request endpoint  |  Mapping: OWASP A07:2021 Identification and Authentication Failures

Description

The endpoint responds differently for registered and unregistered email addresses (a success response versus a server error), allowing an attacker to determine which email addresses have accounts.

Recommendation

Return an identical, generic response regardless of whether the address is registered (for example, "If an account exists, a reset email has been sent").

F-07 — Verbose error messages expose implementation details

LOW-MEDIUM

Component: API request-parsing layer  |  Mapping: OWASP A05:2021 Security Misconfiguration

Description

A malformed JSON request body sent to the API returns a full stack trace to unauthenticated callers, revealing server-side file paths, the web framework and body-parsing dependencies in use, and the serverless runtime layout.

Recommendation

Return generic error messages to clients in production and log full details server-side only.

F-08 — No observed brute-force protection on login

LOW

Component: Login endpoint

Description

Eight consecutive failed login attempts against a test account produced no lockout, CAPTCHA or rate-limiting response.

Recommendation

Introduce progressive delays, CAPTCHA or temporary lockout after repeated failures, or confirm that equivalent controls already exist at the network or WAF layer.

F-09 — Overly permissive CORS policy

LOW

Component: API host

Description

The API returns Access-Control-Allow-Origin: * for arbitrary origins. Because credentials are not allowed cross-origin and the application attaches its token manually, this is not independently exploitable today, but it is unnecessary exposure.

Recommendation

Restrict allowed origins to the application's own front-end origins.

Remediation evidence

The client's own remediation pass fixed 12 insecure-randomness alerts between the previous and latest scan, spanning OAuth/Google login, Stripe payment handling, an AI/protocol utility, and automated scenario-execution routes. This is a positive indicator of active maintenance, though it did not extend to the five game/services/* instances that remain open above.

Dismissed findings relevant to this engagement's AI/LLM scope

Of the 142 alerts the client reviewed and dismissed (as false positive or accepted risk, with a recorded justification), most are low pentest relevance given the stated code context. A smaller subset concerns AI-generated and administrator-authored content rendering paths:

  • A DOM-based XSS alert in the game application's TextViewer component, which by name likely renders AI-generated scenario/benchmark text to learners, was dismissed as a false positive on the basis that the rendered value is always a URL, not markup.
  • Several DOM-based XSS alerts in the admin dashboard's work-model and scenario-configuration components, and in a utility that builds AI/expert review text, were dismissed on the basis that the rendered values are image references or author-only previews.

These are recommended candidates for indirect prompt injection and insecure output handling (LLM02) follow-up, since they concern admin-authored content and AI-generated output paths.
